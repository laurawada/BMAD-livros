BMad Architecture · Validate

Architecture Spine Review

Target: ARCHITECTURE-SPINE.md · Scope: initiative spine for CAP-1 through CAP-6

Verdict: Needs revision before handoff.
The spine covers the core architecture and its deterministic lint passes, but two decisions leave behavior/security open to incompatible implementations. The dependency diagram also conflicts with its stated inward-dependency rule.

Findings

High · Authorization

RPC security mode is not bound

Invariants & Rules · AD-2 and AD-6

AD-2 puts combined writes in a server-only transaction/RPC and AD-6 makes RLS authoritative, but does not bind the function execution mode or equivalent privilege checks. A definer-security function can bypass table RLS, allowing mutation paths to enforce different ownership rules.

Clear fix: Require invoker security with verified claims/RLS, or specify and test explicit ownership checks, restricted execute grants, and hardened definer configuration.

High · Data mutation

Vibes cannot persist for an unadopted book

Invariants & Rules · AD-2; Capability → Architecture Map · CAP-4

AD-2 permits a local book upsert only on shelving or reviewing. CAP-4 writes BookVibe rows that reference a book. A vibe-only action has no permitted way to create that book row.

Clear fix: Make the first vibe mutation an atomic adoption/upsert trigger, or explicitly constrain CAP-4 to books already adopted. The latter narrows the current product contract.

Medium · Dependency boundaries

Diagram and prose disagree about dependency direction

Design Paradigm

The prose says dependencies point inward, while the diagram draws application code toward infrastructure adapters (APP → DB, APP → BOOKS). Those arrows make sense as runtime calls, but are not labeled as such and contradict compile-time dependency direction.

Clear fix: Label the existing diagram as runtime flow and add a compile-time dependency graph showing adapters implement ports owned by the inward layers.

Low · Environment parity

PostgreSQL major version parity is unstated

Deferred · PostgreSQL major version

Separate development and production projects may choose different supported majors unless parity is explicit.

Clear fix: Defer the exact selection until provisioning, but require the same supported major in every environment.
